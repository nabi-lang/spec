# 0.5. 标准库层级

标准库分为三个包层级：`bare`、`core` 和 `std`，每个层级都是一个独立的路径根（`core::List`、`std::fs`）。它们按可用的环境以及所暴露行为的风险来区分。

## 0.5.1. 三个层级

整体结构如下。

```
  bare   ←   no safety guarantees. Raw memory, FFI, transmutable bit casts.
     ↑
  core   ←   safe foundation available on every target. Uses bare internally.
     ↑
  std   ←   target-dependent tier. File system, network, OS threads, etc.
```

箭头表示依赖的方向。`core` 可以在其内部实现中使用 `bare`，`std` 可以同时使用 `core` 和 `bare`。禁止反方向的依赖。

每个层级的名称是其路径的开头（[5.7.4](../005-modules/507-paths.md#574-std-core-bare-the-standard-library-tiers)）。这些名称不是关键字：用户模块或依赖别名可以使用它们，而 `::std::..` 仍然能越过它访问到标准库。

## 0.5.2. 各层级的职责

### `bare`

`bare` 是低层的危险领域。编译器无法保证安全性的行为集中在这里；代表性的项包括裸指针形式（裸指针抽象）和任意位转换（类似 `transmute`）。固定（pinning）、volatile 内存访问以及与 C [ABI](007-glossary.md#abi-application-binary-interface) 兼容的内存分配原语也属于 `bare`。

调用这一层级函数的一方对安全负责，路径本身就清楚地表明了这一点。

### `core`（基础）

`core` 是最常用的安全库；基础部分的所有模块都在这里（例如 `core::collections`、`core::iter`、`core::ops`）。它必须在本规范保证的每个构建目标上以相同的方式可用。它的内容非常广泛：数值、字符和字符串类型及其方法，以及集合类型（列表、映射、集合、元组）。它包含算术、比较、逻辑和位运算符的 trait 定义，还提供迭代器、流和 future。并发原语（原子、互斥锁、通道）以及任务和并行执行的 API 接口也属于这一层级。最后，它涵盖格式化、显示、调试、反射和检查。

可移植的 SIMD 向量是 `core::simd`；张量、自动微分、GPU 等加速领域不属于 `core`；它们由外部库实现，并通过计划在后续版本中提供的后端接口接入编译器的后端。标准库只负责普通代码的表层语义，把加速领域留给库层面的决定。

`core` 的常用项之所以可见，是因为编译器在每个 Nabi 源文件开头隐式应用了 `use core::prelude::*;`。也就是说，`core::collections::List` 可以写作 `List`，`core::task::sleep` 可以写作 `task::sleep`。prelude 的列表固定在 [stdlib 0.2.3](../../refs-standard-libraries/000-meta/002-import.md) 中。

只有 prelude 中的项不需要 `use` 就可见。`core` 的其他每个 `pub` 项都要通过其模块（`ops::Add`、`num::Zero`）或 `use` 访问；`core` 中没有 `pub` 的项是它私有的，与任何包一样（5.6）。

### `std`

`std` 是只在特定环境中（主要在操作系统之上）才有意义的领域。它包含文件系统和网络、时间和时钟、标准 I/O、环境变量、进程，以及对操作系统线程的直接控制。

`std` 的函数在某些目标上可能不存在。在某些领域没有意义的环境中（例如在浏览器内运行的笔记本内核），相应的模块不会被构建。

## 0.5.3. 可见性约定

可见性规则如下。

| 领域            | 隐式导入        | 需要显式导入             | 说明                                          |
|-----------------|-----------------|--------------------------|-----------------------------------------------|
| `core`     | ✓ 仅 prelude 项 | ✓ 其他项需要         | 自动应用 `use core::prelude::*;`                 |
| `bare::**` | ✗               | ✓ 必需                   | 让危险信号在代码中可见                        |
| `std::**` | ✗               | ✓ 必需                   | 让目标依赖在代码中可见                        |
| 用户包          | ✗               | ✓ 必需                   | 其他包的项                                    |

“引入”的具体语法（`use`、`import` 等）在模块系统规范中定义。

## 0.5.4. 分发形式与链接机制

三个层级以源代码形式的库包随编译器一起分发：

```
lib/nabi/bare/src/lib.nabi
lib/nabi/core/src/lib.nabi
lib/nabi/std/src/lib.nabi
```

编译器在首次使用时把它们构建到自己的缓存中，并自动链接（[9.2.19](../009-tools/902-aot-pipeline.md#9219-installation-layout)）。这条路径与用户包的普通依赖相互独立，所以碰巧同名的用户包（例如 `mod bare`、`mod std`）不会冲突。

与编译器本身一样，三个层级遵循零依赖原则。构建用户包时只链接它需要的层级，生成的产物不需要额外的外部库。

## 0.5.5. 为什么是三个层级

如果只有两个层级（安全、危险），就无法区分“在任何地方都安全”和“只有在有操作系统时才安全”，而且在缺少部分操作系统功能的环境（浏览器笔记本等）中，这种划分就会失效。反过来，四个或更多层级会增加用户必须记住的规则，并削弱模块边界的价值。

三个层级是在实践中得到充分验证的划分，也是仍然有意义的最简单划分。

以各自的根来命名每个层级，使路径保持简短并降低学习成本：`core` 通过 prelude 在任何地方都在作用域中，`std::fs` 一看便知是什么，`bare` / `core` / `std` 之间的职责划分可以逐步学会。
