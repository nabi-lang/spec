# 7.3. GC 算法

Nabi 的 GC 是在 [Immix](../000-meta/007-glossary.md#immix) mark-region[^immix] 之上叠加 sticky mark-bit 分代回收[^whippet]的回收器。minor 回收和疏散会全局停顿（stop-the-world），mutator 停在安全点上（[8.4](../008-abi/804-safepoint.md)）。完整回收的标记阶段可以并发运行（[7.5](705-concurrent-collection.md)）。根与写屏障定义在 [7.4](704-barriers-and-roots.md) 中。

> [!NOTE]
> 本节是资料性的：它描述参考运行时的 GC，可能在任何版本中改变。只有在 [8.1](../008-abi/801-object-header-abi.md) 中作为 ABI 固定的对象布局是规范性的。

## 7.3.1. Immix mark-region

### 块与行

```
block (32 KiB) = line (128 B) × 256
```

[块](../000-meta/007-glossary.md#block块)从操作系统获得（mmap）。对象可以跨越行边界。标记阶段同时标记对象及其所跨越的行，清除阶段回收未标记的行。存活对象之间的小空隙以行为粒度重新利用。

### 清除：块的分类

| 类别       | 状态                          | 处理                             |
|------------|-------------------------------|----------------------------------|
| clean      | 所有行为空                    | 放入空闲池                       |
| recyclable | 只有部分行存活                | 空闲行重新用于分配               |
| full       | 几乎所有行都存活              | 保持原样                         |

清除阶段不会把死对象清零，机密缓冲区（`WIPE`，[7.1.2](701-object-layout.md#712-内存空间)）除外。分配器在填充 TLAB 时把行清零。

### 机会式疏散

完整回收可以把存活对象从碎片化的块移到其他块中。

- 候选块根据上一次清除留下的行状态选出（至多半满的块）。此后交出的行视为已占用：其中对象的存活情况尚未可知。只有在超过碎片化阈值时才移动对象。
- 被移动对象的旧位置上会留下转发指针，所有精确引用在同一次回收内更新为新位置。
- 不移动的对象：根直接指向的对象（[7.4.1](704-barriers-and-roots.md#根指向的对象不会被移动)）、被不确定字（`AMBIGUOUS`：类型 id 为 `2` 的缓冲区、无标签的 `union`）指向的对象、`PINNED` / `NOMOVE` 对象，以及 LOS 对象。
- 超出下一周期分配预算的空闲块归还给操作系统。
- 用于测试时，`NABIR_GC_EVAC=always` 会在每次完整回收时进行疏散（[9.9.8](../009-tools/909-debug-tools.md#998-内存--gc-工具)）。

## 7.3.2. Sticky mark-bit 分代回收

没有单独的新生代空间；各代由头中的 `STICKY` 位区分（[8.1.3](../008-abi/801-object-header-abi.md#813-gc_flags偏移-4u32)）。在一次回收中存活下来的对象会被设置 `STICKY`，成为老对象。对象保持原位，没有晋升复制。

| 回收          | 标记起点                                         | 范围                                          |
|---------------|--------------------------------------------------|-----------------------------------------------|
| minor（年轻代） | 根、记忆集、脏卡（[7.4.2](704-barriers-and-roots.md#742-写屏障对象记忆)） | 不进入老对象。清除只覆盖自上次回收以来交出的块（以及在并发标记之后，并发标记期间交出过行的块） |
| full（老年代）  | 根                                               | 清除所有 `STICKY`，执行完整的标记 / 清除 |

- 只在对象查找到达的块中解析年轻行。
- minor 回收的簿记跟随变化，而不是跟随整个堆：含有空闲行的块列表从一次回收保留到下一次，只有此后交出的块才会被重新清除和列出。脏卡以一个字（8 张卡）为单位扫描。
- 当老对象的字节数达到 `max(4 MiB, live after the previous full collection × 2)`，或调用 `nabi_gc_collect` 时，进行完整回收。

## 7.3.3. 标记过程

1. 从根开始（[7.4.1](704-barriers-and-roots.md#741-根跟踪编译器直接生成的影子栈)）。
2. 对每个到达的对象，在头中设置 `MARK`，标记它跨越的行，并通过其 `type_id` 的 [ScanTable](../008-abi/802-scan-table.md) 跟随其子对象。
3. 队列为空时结束。

在全局停顿期间，一旦队列中的工作足够分摊，标记就在多个线程上运行（`NABIR_GC_WORKERS` 个辅助线程，[9.9.8](../009-tools/909-debug-tools.md#998-内存--gc-工具)）：每个线程从自己的栈开始标记，并通过共享池传递工作；`MARK` 用原子 `fetch_or` 设置，因此每个对象只扫描一次；一个块的年轻行由一个线程解析，其他线程等待。并发标记（[7.5](705-concurrent-collection.md)）在其标记线程和协助它的线程上运行。

ScanTable 通过 `nabi_gc_register_type` 注册（[8.5.1](../008-abi/805-extern-symbols.md#851-gc-区域)）。

## 7.3.4. 迁移（热重载）

在 `nabi dev`（[9.14](../009-tools/914-hot-reload.md)）下，热包的新版本可能改变某个类型的布局。其对象在一次迁移中被改写：这是一次全局停顿的完整回收，其最后阶段在标记与清除（以及可能的疏散）之后，改写每个类型已改变的存活对象。

- 哪些对象：热构建为每个按值持有热类型的盒子和缓冲区分配独立的类型 id，因此类型 id 同时指明类型和版本。受影响的类型是已改变的类型，以及每个按值持有这类类型的类型。
- 怎样改写：保留的字段按名称（或 `#[renamed_from]`）复制，新增的字段取停顿之前由其默认值产生的值，删除的字段被丢弃，枚举变体按名称匹配（[9.14.3](../009-tools/914-hot-reload.md#9143-允许哪些变化)）。新布局放得下的对象就地改写；其他对象被复制到新对象中，并像疏散那样转发，指向它的每个堆引用都会被修正，包括指向缓冲区内部的引用和弱引用单元。根字永远不会被改写。
- 先做一次预演：在以下情况下，迁移什么也不做，变更等待：类型已改变的、被根引用的、`PINNED` 或 `NOMOVE` 的对象必须变大；某个不确定字指向一个要移动的对象的中间；某个 `any` 内联持有类型已改变的值；旧代码的闭包、协程或函数值持有或使用了已改变的类型；某个存活的枚举值持有新版本已删除的变体；或者某个不回收区间处于打开状态。
- 在 GC 统计中，一次迁移计为一次完整回收。
