# 0.5. 표준 라이브러리 계층

표준 라이브러리는 세 패키지 계층 `bare`, `core`, `std`로 나뉘며, 각 계층이 자기 경로 루트입니다(`core::List`, `std::fs`). 나누는 기준은 쓸 수 있는 환경과 드러내는 동작의 위험도입니다.

## 0.5.1. 세 계층

전체 구조는 다음과 같습니다.

```
  bare   ←   안전 보장 없음. 원시 메모리·FFI·전송 가능 비트 캐스팅.
     ↑
  core   ←   모든 타깃에서 사용 가능한 안전 foundation. 내부적으로는 bare 를 쓴다.
     ↑
  std   ←   타깃 종속 계층. 파일 시스템·네트워크·OS 스레드 등.
```

화살표는 의존 방향입니다. `core`는 `bare`를 내부 구현에 쓸 수 있고, `std`는 `core`와 `bare`를 모두 쓸 수 있습니다. 반대 방향으로는 의존할 수 없습니다.

각 계층의 이름이 그 경로를 시작합니다([5.7.4](../005-modules/507-paths.md#574-std-core-bare-표준-라이브러리-계층)). 이 이름들은 키워드가 아닙니다. 사용자 모듈이나 의존성 별칭이 차지할 수 있고, 그래도 `::std::..`는 라이브러리에 닿습니다.

## 0.5.2. 각 계층의 책임

### `bare`

`bare`는 저수준의 위험한 영역입니다. 컴파일러가 안전성을 보증할 수 없는 동작이 여기에 모입니다. 대표적으로 원시 포인터 형태(raw pointer 추상)와 임의 비트 캐스트(`transmute` 류)가 있습니다. 핀(pinning), volatile 메모리 접근, C [ABI](007-glossary.md#abi-application-binary-interface) 호환 메모리 할당의 원형도 `bare` 영역입니다.

이 계층의 함수를 호출하는 쪽이 안전성을 책임집니다. 경로 이름 자체가 이 사실을 분명히 드러냅니다.

### `core`(foundation)

`core`는 가장 자주 쓰는 안전한 라이브러리입니다. foundation의 모든 모듈이 여기에 있습니다(예: `core::collections`, `core::iter`, `core::ops`). 이 계층은 이 사양이 보증하는 모든 빌드 타깃에서 똑같이 쓸 수 있어야 합니다. 범위가 넓어서 숫자, 문자, 문자열 타입과 그 메서드, 컬렉션(리스트, 맵, 셋, 튜플)이 들어 있습니다. 산술, 비교, 논리, 비트 연산자의 트레잇 정의와 반복자, 스트림, future도 있습니다. 동시성 프리미티브(atomic, mutex, channel)와 task, 병렬 실행의 API 표면도 이 계층에 속합니다. 형식화, 표시, 디버그, 리플렉션, 인스펙션까지 포함합니다.

이식 가능한 SIMD 벡터는 `core::simd`입니다. 텐서 / 자동 미분 / GPU 같은 가속 영역은 `core`에 들어 있지 않습니다. 외부 라이브러리가 구현하고, 이후 릴리스에 도입할 예정인 백엔드 인터페이스로 컴파일러 백엔드에 닿습니다. 표준 라이브러리는 일반 코드의 표면 의미만 책임집니다. 가속 영역은 라이브러리 계층에서 정합니다.

컴파일러는 모든 Nabi 소스의 시작 지점에 묵시적으로 `use core::prelude::*;`를 적용합니다. 그래서 `core`의 흔한 항목이 보입니다. 예를 들어 `core::collections::List`를 그냥 `List`로, `core::task::sleep`을 `task::sleep`으로 쓸 수 있습니다. prelude 목록은 [stdlib 0.2.3](../../refs-standard-libraries/000-meta/002-import.md)에 정해 둡니다.

`use` 없이 보이는 것은 prelude의 항목뿐입니다. `core`의 다른 `pub` 항목은 모듈을 거치거나(`ops::Add`, `num::Zero`) `use`로 가져옵니다. `pub`이 없는 `core` 항목은 다른 패키지와 마찬가지로 비공개입니다(5.6).

### `std`

`std`는 특정 환경(주로 OS 위)에서만 의미가 있는 영역입니다. 파일 시스템, 네트워크, 시간과 시계, 표준 입출력, 환경 변수, 프로세스, OS 스레드 직접 제어 같은 기능이 들어 있습니다.

`std`의 함수는 타깃에 따라 없을 수도 있습니다. 일부 영역이 의미가 없는 환경(예: 브라우저 안에서 동작하는 노트북 커널)에서는 해당 모듈을 빌드하지 않습니다.

## 0.5.3. 가시 규약

가시성 규칙은 다음과 같습니다.

| 영역           | 묵시 import | 명시 import 필요 | 비고                            |
|----------------|-------------|------------------|---------------------------------|
| `core`     | ✓ prelude 항목만 | ✓ 그 밖의 항목 | `use core::prelude::*;` 자동 적용   |
| `bare::**` | ✗           | ✓ 필요           | 위험 시그널을 코드에 보이도록   |
| `std::**` | ✗           | ✓ 필요           | 타깃 의존성이 코드에 드러나도록 |
| 사용자 패키지  | ✗           | ✓ 필요           | 다른 패키지의 항목              |

"끌어옴"의 구체 구문(`use`, `import` 등)은 모듈 시스템 사양에서 정의합니다.

## 0.5.4. 제공 형태와 링크 메커니즘

세 계층은 소스 형태의 라이브러리 패키지로 컴파일러와 함께 배포합니다.

```
lib/nabi/bare/src/lib.nabi
lib/nabi/core/src/lib.nabi
lib/nabi/std/src/lib.nabi
```

컴파일러는 처음 쓸 때 이들을 캐시에 빌드하고 자동으로 링크합니다([9.2.19](../009-tools/902-aot-pipeline.md#9219-설치-레이아웃)). 이 경로는 사용자 패키지의 일반 의존성과 분리되어 있습니다. 그래서 사용자 패키지의 이름이 우연히 같아도(예: `mod bare`, `mod std`) 충돌하지 않습니다.

세 계층은 컴파일러 자체와 마찬가지로 의존성 0 원칙을 따릅니다. 사용자 패키지를 빌드하면 필요한 계층만 링크됩니다. 결과 산출물에는 외부 라이브러리가 더 필요하지 않습니다.

## 0.5.5. 세 계층으로 나눈 이유

계층이 둘(안전, 위험)뿐이면 "어디서나 안전"과 "OS가 있을 때만 안전"을 구분할 수 없습니다. 그러면 OS 기능 일부가 없는 환경(브라우저 노트북 등)에서 계층 구분이 무너집니다. 반대로 계층이 넷 이상이면 사용자가 외울 규칙이 늘고 모듈 경계의 가치가 떨어집니다.

세 계층은 실무에서 충분히 검증된 구분입니다. 의미가 있는 분할 중 가장 단순하기도 합니다.

계층마다 자기 이름을 루트로 두면 경로가 짧고 학습 비용도 낮습니다. `core`는 prelude로 어디서나 보이고, `std::fs`는 읽히는 그대로입니다. `bare` / `core` / `std` 책임 구분은 차차 익히면 됩니다.
