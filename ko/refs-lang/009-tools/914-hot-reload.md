# 9.14. 핫 리로드

*핫 리로드*는 실행 중인 프로그램에 편집을 적용합니다. `nabi dev`(9.10.8)가 소스가 바뀐 패키지를 다시 빌드하면, 프로그램은 safepoint에서 새 코드를 로드하며 힙, 스레드, static을 그대로 유지합니다. 핫 리로드는 플러그인([9.12](912-plugins.md)) 위에 지은 개발 도구입니다. 로컬 패키지의 코드는 모두 교체할 수 있는 플러그인에 있고, 나머지 프로그램은 실행되는 동안 바뀌지 않습니다.

## 9.14.1. 모델

dev 세션에는 두 종류의 모듈이 있습니다.

- *호스트*: 런타임, 표준 라이브러리의 상태, 그리고 모든 레지스트리 패키지와 git 패키지. 세션마다 한 번 빌드합니다. 호스트는 평범한 플러그인 호스트([9.12.1](912-plugins.md#9121-모델))이며, 그 `main`은 `std::reload::host_main()`입니다. 이것은 dev 채널에 연결하고, `NABI_DEV_PLUGINS`가 가리키는 핫 플러그인을 로드한 뒤 루트 패키지의 `main`(`NABI_DEV_MAIN`)을 부릅니다.
- *핫 플러그인*: 로컬 패키지(루트 패키지, 그 `path` 의존성, 루트가 쓰는 워크스페이스 멤버)마다 하나씩, `nabic build --hot`([9.1](901-nabic-cli.md))으로 빌드합니다. 저장할 때마다 그 저장이 건드린 패키지의 새 버전이 생깁니다.

`--hot`에서는 핫 패키지 함수로 들어가는 호출이 모두 슬롯을 거칩니다. 슬롯의 키는 함수의 맹글링된 이름과 시그니처입니다. 버전을 로드하면 로드된 모든 버전의 각 슬롯을 키가 같은 가장 새 본문에 묶습니다. 따라서 다음과 같습니다.

- 본문이 바뀐 함수는 옛 버전의 코드를 포함해 어디서 부르든 새 형태로 불립니다.
- 시그니처가 바뀐 함수는 새 키와 새 슬롯을 받습니다. 옛 시그니처로 빌드된 호출자는 계속 옛 본문을 부르고, 새 호출자는 새 본문을 부릅니다.
- 옛 버전은 세션이 끝날 때까지 매핑된 채로 남습니다.

핫 패키지의 패키지 해시([9.5](905-symbol-mangling.md))는 세션 동안 고정됩니다(패키지 이름에서 얻음). 그래서 심벌은 버전이 바뀌어도 같은 이름을 유지합니다. 레지스트리 패키지와 git 패키지는 내용 해시를 그대로 씁니다.

`--hot`의 비용은 핫 패키지로 들어가는 호출마다 로드 하나와 간접 분기 하나, 함수를 넘는 핫 함수 인라이닝 없음, 프레임 포인터 유지, 루트 재읽기 규칙([8.4](../008-abi/804-safepoint.md))입니다. 일반 빌드(`nabi build`, `nabi run`)에는 이 중 어느 것도 없습니다. `--hot`은 dev 프로파일만 빌드합니다.

## 9.14.2. 버전이 적용되는 때

프로그램은 dev 채널 스레드에서 버전을 로드하고, 모든 스레드를 멈추는 정지에서 적용합니다. 이 정지는 컬렉션이 쓰는 것과 같습니다([7.3](../007-runtime/703-gc-algorithm.md)).

- 코드만 바뀐 변경은 다음 정지에서 적용됩니다.
- 타입 레이아웃이 바뀐 변경은 바뀐 타입의 값을 쥔 프레임이 없는 첫 정지에서 적용되고(9.14.4), 그때 살아 있는 값을 옮깁니다(9.14.3).
- `std::reload::point()`([3.13](../../refs-standard-libraries/300-std/313-reload.md))는 정지를 요청하며, 레이아웃 변경이 보통 통과하는 곳입니다. `nabi dev` 밖에서는 아무 일도 하지 않습니다.

아직 적용할 수 없는 버전은 대기 상태로 남아 정지마다 다시 시도되고, 다음 저장이 그것을 대체합니다. 결코 적용할 수 없는 버전은 거부되며, 프로그램은 지금 가진 코드로 계속 실행됩니다.

## 9.14.3. 바꿀 수 있는 것

컴파일러는 새 버전의 타입을 실행 중인 버전의 타입(`--hot-base`, 버전마다 옆에 쓰는 `.layout` 파일)과 비교하고, 프로그램이 옮길 수 없는 변경은 컴파일 에러로 거부합니다.

| 변경 | 결과 |
|------|------|
| 기본값이 있는 필드 추가(`mana: i32 = 0;`) | 허용. 살아 있는 값은 기본값을 받음 |
| 기본값이 없는 필드 추가 | 에러: ``new field `mana` needs a default while the program runs: write `mana: i32 = 0;` (or restart with `r`)`` |
| 필드 제거 | 허용. 그 값은 버림 |
| 필드 순서 변경 | 허용 |
| `#[renamed_from("hp")] health: i32`로 필드 이름 변경([6.2](../006-meta-system/602-built-in-attributes.md)) | 허용. 값을 이어받음. 없던 필드를 가리키면 옛 필드 목록을 담은 에러 |
| 필드 타입 변경 | 에러: ``field `hp` of `Player` changed from `i32` to `f64` while the program runs; give the new field its own name with a default (`health: f64 = 100.0`) to start it fresh, or restart with `r` `` |
| 열거형 variant 추가, 순서 변경 | 허용. 태그는 이름으로 대응 |
| 열거형 variant 제거 | 컴파일 때는 허용. 살아 있는 값이 그 variant를 쥐고 있는 동안 버전은 기다림: ``waiting: a live `State::Paused` exists`` |
| variant 페이로드 변경 | variant마다 필드 규칙대로 |
| 제네릭 매개변수 변경, 구조체를 열거형으로 바꿈 | 에러. 재시작 |
| 트레잇 구현 추가, 제거, 변경 | 허용. `any Tr` 디스패치 항목을 교체 |

옮기기는 전체 컬렉션의 마지막 단계입니다. 바뀐 타입의 객체를 새 레이아웃으로 다시 씁니다. 남은 필드는 이름으로(또는 `#[renamed_from]`으로), 추가된 필드는 기본값으로 채우고, 제거된 필드는 버리며, 열거형 variant는 이름으로 대응합니다. 새 레이아웃이 객체 안에 들어가면 제자리에서, 아니면 새 객체로 다시 쓰고, 그 객체를 가리키는 힙 참조를 모두 갱신합니다. 커져야 하는 루트 객체(프레임의 지역 변수, 전역 루트)는 옮기지 않으며 변경을 붙잡습니다(9.14.4). 모든 스레드를 멈춘 첫 검사가 변경을 붙잡는 것을 찾으므로, 실행할 수 없는 옮기기는 아무것도 바꾸지 않습니다.

## 9.14.4. 아직 실행 중인 코드

| 대상 | 규칙 |
|------|------|
| 옛 함수의 프레임 | 옛 코드로 끝까지 실행됨. 그 프레임이 하는 호출은 새 코드에 닿음 |
| `main` 자신의 루프 | 세션 내내 옛 코드. 프레임마다 하는 일은 `main`이 부르는 함수에 둠 |
| 바뀐 타입의 값을 쥔 프레임 | 레이아웃 변경을 붙잡음: ``waiting: `main` (src/main.nabi:12) holds a `World` across `reload::point()`; keep it in a `reload::State`: `let world = reload::State::new(World::new());` ``. `--hot`은 컴파일할 때 같은 곳에 경고함 |
| 클로저 | 만들어질 때의 본문을 유지. 환경이 바뀐 타입을 쥐면 레이아웃 변경을 붙잡음: ``waiting: a closure made in `spawn_wave` (src/wave.nabi:30) holds an old `Enemy` `` |
| 중단된 코루틴이나 태스크 | 옛 코드로 재개. 바뀐 타입을 쥐면 레이아웃 변경을 붙잡으며, 메시지가 생성된 곳을 밝힘 |
| static | 저장소와 값을 유지. 새 static은 초기화식에서 시작. 타입의 레이아웃이 바뀐 static은 옮김 |
| `any Tr` 값 | 가장 새 구현으로 디스패치 |
| 커지는, 바뀐 타입의 루트 객체, 고정(pinned) 객체, 주소를 얻은 객체 | 레이아웃 변경을 붙잡음 |
| 바뀐 타입의 값을 안에 담은 `any`, 열린 no-collect 구간 | 레이아웃 변경을 붙잡음 |

## 9.14.5. dev 채널

`nabi dev`는 프로그램을 시작하기 전에 채널을 만들고, 프로그램의 환경 변수 `NABI_DEV`로 그 이름을 알려 줍니다. 유닉스 스트림 소켓의 경로이거나, Windows에서는 이름 있는 파이프의 이름(`\\.\pipe\nabi-dev-<pid>-<n>`)입니다. 런타임은 `NABI_DEV`가 있으면 시작할 때 연결합니다. 그것 없이 시작한 프로그램은 채널을 열지 않으며, `std::reload::active()`는 거짓입니다.

메시지는 `\n`으로 끝나는 UTF-8 한 줄입니다.

| 보내는 쪽 | 줄 | 뜻 |
|------|------|---------|
| 프로그램 | `hello 1 <pid>` | 첫 줄: 프로토콜 버전 1 |
| `nabi dev` | `load <path>` | 이 파일, 즉 핫 패키지 하나의 새 버전을 로드함. 함께 바뀐 패키지는 의존성을 먼저 하여 여러 줄로 옴 |
| 프로그램 | `applied <pkg> v<n>: <what>` | 버전이 들어감: `applied game v3: 4 functions, 1 type (Enemy: +mana), 120 objects migrated` |
| 프로그램 | `waiting <pkg> v<n>: <why>` | 아직 아님(9.14.4). 이유가 바뀌면 다시 보냄. 같은 로드의 마지막 줄이 뒤에 옴 |
| 프로그램 | `refused <pkg> v<n>: <why>` | 버전은 적용되지 않음. 프로그램은 자기 코드를 유지 |
| 프로그램 | `superseded <pkg> v<n>` | 기다리는 동안 같은 패키지의 더 새 `load`가 이것을 대체함 |

`<pkg>`는 코드에 쓰는 패키지 이름이고, `<n>`은 프로그램이 세는 버전입니다(1은 시작할 때의 버전). 로드는 보낸 순서대로 적용되며, 기다리는 로드는 그 뒤의 로드를 붙잡습니다. 같은 패키지의 더 새 로드는 기다리는 로드의 자리를 차지합니다. `load`마다 마지막 답(`applied`, `refused`, `superseded`)이 정확히 하나 옵니다. 한 패키지의 답은 그 로드 순서대로 오지만, 다른 패키지끼리는 그렇지 않을 수 있습니다. `nabi dev`는 다음 `load`를 보내기 전에 답을 기다리지 않습니다. 모르는 줄에는 `refused <line>: unknown request`로 답합니다. 채널이 끝나면 프로그램이 끝난 것입니다.

## 9.14.6. 핫 리로드에 없는 것

- 레지스트리 패키지와 git 패키지, 호스트, `nabi.nabion`: 이것이 바뀌면 프로그램을 재시작합니다(9.10.8).
- 필드 값을 새 타입으로 변환하기.
- 이미 있는 클로저를 새 본문으로 옮기기.
- C 프레임에 있는 값: C 콜백 아래의 핫 프레임은 레이아웃 변경을 붙잡습니다.
- wasm 타깃, 릴리스 빌드, REPL.
- 배포된 프로그램이 로드하는 플러그인 다시 로드하기: 핫 리로드는 `nabi dev` 전용입니다.
