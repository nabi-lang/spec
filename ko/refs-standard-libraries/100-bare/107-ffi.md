# 1.7. FFI: `extern "C"` / `CStr` / `CString` / `CPtr`

`bare::ffi` 모듈은 C ABI와 호환되는 외부 함수와 데이터를 정의하는 메커니즘입니다. [refs-lang 5.9 extern 블록](../../refs-lang/005-modules/509-extern-block.md)이 정의하는 `extern "C" { ... }` 블록과 함께 동작합니다.

`CStr` / `CString` 말고도 이 모듈에는 C의 타입(`types`, prelude에도 있음, 1.7.9), C가 쥐는 Nabi 값을 위한 `Handle`(1.7.10), 저장된 errno(1.7.11), `wchar_t` 문자열(1.7.12), 공유 라이브러리를 불러오는 `Library`(1.7.13)가 있습니다.

이 장은 전통적인 C FFI만 다룹니다. WASM Component Model 기반 FFI는 [1.8 wit](108-wit.md)에서 따로 설명합니다.

## 1.7.1. `extern "C"` 블록

가장 기본 형태는 다음과 같습니다.

```nabi
extern "C" {
    // 함수 선언
    fn malloc(size: usize) -> CPtr<u8>;
    fn free(ptr: CPtr<u8>);
    fn strlen(s: ConstPtr<c_char>) -> usize;

    // 글로벌 (read-only)
    static environ: CPtr<CPtr<c_char>>;

    // 글로벌 (mutable): `mut` 키워드 _이 자리에서만_ 허용
    static mut atexit_count: u64;
}
```

C의 `errno`는 전역 변수가 아니라 스레드마다 다른 매크로이므로 `static`으로 선언할 수 없습니다. `#[errno]`가 호출 뒤에 errno를 저장합니다(1.7.11). C의 정수 타입은 C 이름(`c_int`, `c_long`, `c_size_t`, 1.7.9)으로 씁니다. 이 이름은 모든 타깃에서 크기가 맞습니다.

여기 나오는 `mut` 키워드는 [refs-lang 1.5 키워드](../../refs-lang/001-lexical/105-keywords.md)에서 정의합니다. 이 위치에서만 의미가 있고, 일반 변수에는 쓸 수 없습니다.

### `#[link("name")]`: 라이브러리 지정

라이브러리를 명시적으로 지정하려면 `#[link]` 속성을 씁니다.

```nabi
#[link("c")]
extern "C" {
    fn malloc(size: usize) -> CPtr<u8>;
    fn free(ptr: CPtr<u8>);
}

#[link("m")]
extern "C" {
    fn cos(x: f64) -> f64;
    fn sin(x: f64) -> f64;
}
```

링커가 `-lc`나 `-lm` 같은 플래그를 자동으로 붙입니다.

### 호출 규약(calling convention)

C 코드에 쓸 수 있는 호출 규약은 두 가지입니다. `"nabi"`는 런타임 ABI입니다([refs-lang 5.9.2](../../refs-lang/005-modules/509-extern-block.md#592-abi-명시)). 그 밖의 ABI 문자열은 에러(E0025)입니다.

```nabi
extern "C" { ... }              // System V (Unix) / Microsoft x64 (Windows)
extern "system" { ... }         // Windows: stdcall on x86, C on x64 / aarch64
```

대부분은 기본값인 `"C"`면 충분합니다. `"system"`은 주로 **Windows API**를 다룰 때 씁니다.

### `#[leaf]`: 짧은 호출

```nabi
#[leaf]
extern "C" {
    fn abs(x: c_int) -> c_int;
    fn labs(x: c_long) -> c_long;
}
```

모든 `extern "C"` 호출은 호출하는 스레드를 park합니다. C가 도는 동안 그 스레드는 수집기에게 멈춘 것으로 치므로, 호출 중에 수집이 돌 수 있습니다(1.7.7, [refs-lang 8.4.10](../../refs-lang/008-abi/804-safepoint.md#8410-네이티브-호출)). 블록이나 선언 하나에 `#[leaf]`를 붙이면 그 감싸기를 빼므로 짧은 호출이 싸집니다. leaf 함수는 곧 돌아와야 하고, 블록하면(lock, I/O, sleep) 안 되며, Nabi를 다시 불러서도 안 됩니다. 도는 동안 그 스레드가 프로세스의 모든 수집을 붙잡으므로, 블록하는 leaf는 할당하는 모든 스레드를 멈춰 세웁니다. debug toolchain은 leaf 호출 안에서 스레드가 수집 때문에 멈추는 일이 없는지 검사합니다. `extern "nabi"` 블록의 `#[leaf]`는 에러입니다(1.7.11).

### `str` 매개변수와 반환

`extern "C"` 함수의 `str` 매개변수는 NUL로 끝나는 `char*`로 전달됩니다([refs-lang 5.9.4](../../refs-lang/005-modules/509-extern-block.md#594-ffi-호환-타입)). 돌려받은 `char*`의 바이트는 C의 것이므로 `str` 결과는 에러입니다. 결과를 `ConstPtr<c_char> | none`으로 선언하고 `CStr::from_ptr`(1.7.2)로 복사합니다. `(ptr, len)` 전달은 런타임 ABI `extern "nabi"`의 방식입니다([5.9.2](../../refs-lang/005-modules/509-extern-block.md#592-abi-명시)).

```nabi
extern "C" {
    fn puts(s: str) -> i32;          // "hi" → NUL 로 끝나는 char*
    fn getenv(name: str) -> CPtr<c_char>;   // null 가능, CPtr 로 받음
}
```

### C 컴파일러와 플랫폼 ABI

타깃마다 C ABI는 플랫폼의 ABI 문서를 따릅니다. System V psABI(x86-64, i386), AAPCS64, VFP를 쓰는 AAPCS32, RISC-V psABI, ELFv2, s390x ELF ABI, WebAssembly C ABI, Microsoft의 x64 / x86 / ARM64 규약입니다. toolchain의 테스트는 생성한 시그니처 표(struct, union, 동종 부동소수 집계, `f16` / `bf16`, `Simd`, 과정렬과 packed struct, 레지스터 소진, 가변 인자 꼬리, 모든 크기의 결과, 양방향)로 각 타깃을 그 라이브러리를 빌드하는 C 컴파일러와 맞춰 봅니다. Linux에서는 gcc 15.2와 clang 21(x86-64, i686, aarch64. armv7, riscv64, powerpc64le, s390x는 테스트 머신에 교차 gcc가 없어 clang만), macOS에서는 Apple clang 21, Windows x64와 i686에서는 MSVC 14.44(`cl`, 기준)와 clang-cl 22, Windows ARM64에서는 MSVC 14.44와 clang입니다.

컴파일러끼리 다르면 문서를 따릅니다.

- AArch64 집계 안의 `__bf16`: AAPCS64는 이를 반정밀도 부동소수로 셉니다. 그래서 `__bf16`로 된 struct는 동종 부동소수 집계로 `v` 레지스터에 들어가며, clang도 그렇게 넘깁니다. gcc 15.2는 그런 struct를 정수 레지스터로 넘깁니다. gcc로 빌드한 C 라이브러리라면 C 쪽 필드를 `uint16_t`로 선언합니다.
- i686의 `f16` / `bf16`: gcc는 SSE2가 있을 때만(`-msse2`, nabi의 i686 타깃이 전제하는 기준) `_Float16`을 넘기며, clang과 같습니다.
- MSVC는 과정렬 멤버를 담은 packed struct를 그 멤버의 정렬로 배치합니다. nabi도 `*-windows-msvc` 타깃에서는 그렇게 하고, 다른 곳에서는 GNU 배치를 씁니다.

다루지 않는 것: 8바이트보다 넓은 `long double`, `__int128`, `_Complex`(nabi 형태 없음), C++의 빈 struct(C에는 없음).

## 1.7.2. `CStr` / `CString`: null 종료 문자열

`CStr`는 C 문자열을 다루는 빌림(borrow) 타입입니다.

```nabi
struct CStr {
    // 내부: 바이트와 마지막 NUL 을 str 객체 하나에 담음
}

impl CStr {
    unsafe fn from_ptr(p: ConstPtr<c_char>) -> CStr | none;
                                    // NUL 까지 복사; null pointer → none
                                    // p 는 null 이거나 살아 있는 NUL 종료 문자열을 가리켜야 함

    fn from_bytes_with_nul<B: AsBytes>(bytes: B) throws (FromBytesWithNulError) -> CStr;
                                    // 검증: 마지막이 0, 중간 0 없음
    fn from_bytes_until_nul<B: AsBytes>(bytes: B) throws (FromBytesUntilNulError) -> CStr;
                                    // 첫 0 앞까지의 바이트 (고정 크기 C 버퍼)

    fn as_ptr(self) -> ConstPtr<c_char>;
    fn as_bytes(self) -> Slice<u8>;            // null-terminator 제외
    fn as_bytes_with_nul(self) -> Slice<u8>;   // null-terminator 포함
    fn to_str(self) throws (Utf8Error) -> str;  // UTF-8 변환

    fn len(self) -> usize;                     // null-terminator 제외
}
```

`from_ptr`는 C 문자열을 NUL까지 복사해 옵니다. 그래서 결과는 언제나 올바른 C 문자열입니다. `from_ptr`는 `unsafe fn`입니다. 매달린 포인터나 NUL 없는 바이트를 가리키는 포인터는 정의되지 않은 동작입니다. 모든 생성 함수가 복사하므로 바이트 검사에 드는 비용이 따로 없고, 검사하지 않는 형태도 없습니다. `from_bytes_until_nul`은 NUL 뒤가 쓰레기 값인 고정 크기 C 버퍼를 읽습니다. `CStr` / `CString`은 바이트와 NUL을 GC 객체 하나에 담습니다. `as_ptr`는 `str::as_ptr`와 같은 기간 동안 유효합니다([2.15.2](../200-core/215-string.md#2152-str-불변-utf-8-문자열)). 포인터 값이 나올 수 있는 함수에서 그 `CStr` / `CString`을 담은 변수가 스코프 안에 있는 동안입니다.

### `CString`: 소유하는 null 종료 문자열

직접 소유하는 형태가 필요하면 `CString`을 씁니다.

```nabi
struct CString { /* GC heap, null-terminated */ }

impl CString {
    fn new<B: AsBytes>(bytes: B) throws (NulError) -> CString;
                                        // 중간 null byte 거부; str 은 UTF-8 바이트를 줌

    fn as_c_str(self) -> CStr;
    fn as_ptr(self) -> ConstPtr<c_char>;
    fn into_bytes(self) -> List<u8>;     // owned bytes (null 제외)
    fn into_bytes_with_nul(self) -> List<u8>;
}
```

에러 타입은 바이트가 어디서 어긋났는지 알려 줍니다. 모두 `Display`(`message()`), `Debug`, `Error`, `PartialEq`, `Eq`, `Clone`을 구현하며, `NulError`의 필드는 비공개입니다([0.5.10](../000-meta/005-notation.md)).

```nabi
struct NulError { .. }
impl NulError {
    fn position(self) -> usize;     // 중간 NUL 의 index (CString::new)
    fn message(self) -> str;        // "nul byte found at position 1"
}

enum FromBytesWithNulError {       // CStr::from_bytes_with_nul
    InteriorNul { position: usize; },   // 마지막 바이트 앞의 NUL
    NotNulTerminated,                   // 마지막 바이트가 NUL 이 아님
}
impl FromBytesWithNulError {
    fn message(self) -> str;        // "interior nul byte at 3"
}

struct FromBytesUntilNulError;    // NUL 이 아예 없음 (CStr::from_bytes_until_nul); message()
```

### 예: strlen

```nabi
extern "C" {
    fn strlen(s: ConstPtr<c_char>) -> usize;
}

let s: str = "hello";
let cs = try CString::new(s);
let n = unsafe { strlen(cs.as_ptr()) };       //→ 5
```

> [!NOTE]
> `str`와 `CStr` 사이의 변환에는 **할당이 필요합니다**. null 종료 문자를 추가해야 하기 때문입니다. `str`는 보통 null로 끝나지 않으므로 FFI 호출 지점에서만 명시적으로 변환하기를 권장합니다.

## 1.7.3. `CPtr<T>`와 null 가능성

기준 정의는 [1.1.5 CPtr](101-ptr.md#115-cptrt-c-호환-null-가능)에 있습니다. C 함수가 `T*`를 반환할 때는 null 가능성을 명시해야 합니다. 이때 쓰는 타입입니다.

```nabi
extern "C" {
    fn fopen(path: ConstPtr<c_char>, mode: ConstPtr<c_char>) -> CPtr<FILE>;
    fn fclose(file: CPtr<FILE>) -> i32;
}

struct FILE;        // opaque

let path = try CString::new("data.txt");
let mode = try CString::new("r");
let f: CPtr<FILE> = unsafe { fopen(path.as_ptr(), mode.as_ptr()) };

match f.as_ptr() {
    file: Ptr<FILE> => {
        // 사용
        unsafe { fclose(f) };
    }
    none => panic("fopen failed"),
}
```

## 1.7.4. `using` 블록: RAII

GC는 finalizer를 실행하지 않습니다. 그래서 외부 자원은 `Drop`으로 해제하고, 컴파일러가 정해진 지점에서 `Drop`을 부릅니다. 값의 소유자가 스코프를 벗어나는 곳(모든 탈출 경로)이나, 값을 묶은 `using` 블록이 끝나는 곳입니다([2.13.4](../200-core/213-marker.md#2134-drop-해제-시-정리)). `bare::ffi`에는 자체 파일 API가 없습니다. 아래 래퍼는 C 함수를 직접 선언하고 `Drop`에서 핸들을 닫습니다.

```nabi
struct FILE;        // opaque (1.7.3)

#[link("c")]
extern "C" {
    fn fopen(path: ConstPtr<c_char>, mode: ConstPtr<c_char>) -> CPtr<FILE>;
    fn fclose(file: CPtr<FILE>) -> i32;
}

// 사용자가 쓴 C handle 소유자; Drop 이 닫음
struct File { raw: CPtr<FILE>; }

impl Drop for File {
    fn drop(ref self) { unsafe { fclose(self.raw) }; }
}

fn open(path: str) -> File {
    let p = try! CString::new(path);
    let m = try! CString::new("r");
    let raw = unsafe { fopen(p.as_ptr(), m.as_ptr()) };
    if raw.is_null() { panic("fopen failed"); }
    File { raw }
}

using f = open("data.txt") {
    process(f);
}     // ← scope 끝에서 자동 fclose (Drop)

// without using: `f`가 스코프를 벗어나는 곳에서 해제
fn run() throws {
    let f = open("data.txt");
    try process(f);               // 에러가 전파되어 나가도 fclose 실행
}                                 // ← 여기서 fclose (Drop)
```

`using` 구문 자체는 [refs-lang 3.17 using 표현식](../../refs-lang/003-expressions/317-using-expression.md)이 정합니다. 이 구문은 [2.13 marker](../200-core/213-marker.md)의 `Drop` 트레잇과 맞물려 동작합니다.

## 1.7.5. 안전 래퍼 패턴: sys와 safe 분리

Rust 생태계의 표준 관용구는 `*-sys` 크레이트(원시 FFI)와 같은 이름의 크레이트(안전한 래퍼)를 나누는 방식입니다. Nabi도 같은 패턴을 권장합니다.

```nabi
// libc-sys 모듈: raw FFI
mod c {
    #[link("c")]
    extern "C" {
        pub fn malloc(size: usize) -> CPtr<u8>;
        pub fn free(ptr: CPtr<u8>);
        pub fn strdup(s: ConstPtr<c_char>) -> CPtr<c_char>;
    }
}

// libc: safe wrapper
pub struct AllocError { pub size: usize; }

pub fn alloc_buffer(size: usize) throws (AllocError) -> List<u8> {
    let p = unsafe { c::malloc(size) };
    match p.as_ptr() {
        ptr: Ptr<u8> => {
            // unsafe → safe 경계
            let bytes = unsafe { ptr.as_many().slice(size).to_list() };
            unsafe { c::free(p) };
            bytes
        }
        none => { throw AllocError { size }; }
    }
}
```

이렇게 나누면 unsafe 코드가 좁은 영역에 갇힙니다. 사용자 코드는 안전한 래퍼만 호출하므로 안전합니다.

## 1.7.6. 자동 바인딩 생성

`nabi bindgen`([refs-lang 9.10.8](../../refs-lang/009-tools/910-nabi-frontend.md#nabi-bindgen-c-헤더-바인딩))은 C 헤더에서 Nabi 선언을 생성합니다. 헤더는 toolchain의 C 컴파일러 `nabicc`([refs-lang 9.13](../../refs-lang/009-tools/913-c-compiler.md))의 프런트엔드로 읽습니다. 이 프런트엔드는 타깃의 C 컴파일러와 같은 방식으로 C를 전처리하고, 파싱하고, 레이아웃을 정합니다. 다른 C 컴파일러도 libclang도 필요하지 않습니다.

```bash
nabi bindgen libfoo.h > libfoo_sys.nabi
nabi bindgen libfoo.h --target=x86_64-pc-windows-msvc -o libfoo_sys.nabi -- -I include -DFOO=1
```

출력은 타깃 하나(`--target`, 기본값은 호스트)용입니다. 크기, 레이아웃, 정수 폭은 그 타깃의 C ABI를 따릅니다. `--` 뒤의 인자는 C 컴파일러 옵션입니다([refs-lang 9.10.8](../../refs-lang/009-tools/910-nabi-frontend.md#nabi-bindgen-c-헤더-바인딩)). 기계의 시스템 헤더는 세 경우에 씁니다. 그 기계 자신의 플랫폼, Apple 타깃(SDK), MSVC 호스트의 MSVC 타깃(`INCLUDE`, 없으면 가장 새 Visual Studio와 Windows SDK)입니다. 그 밖의 타깃에서는 `--` 뒤에 `--sysroot`를 주지 않는 한 컴파일러의 내장 헤더(`stddef.h`, `stdint.h`, `stdarg.h`, `stdbool.h`, `limits.h`, `float.h` 등)만 씁니다. 타깃의 헤더는 `--` 뒤에(`-isystem <dir>`) 넘깁니다. 출력에는 헤더의 선언과, 그 헤더가 포함(include)하는 비시스템 헤더의 선언을 씁니다. 시스템 디렉터리의 헤더라면 자기 디렉터리 트리에서 포함하는 헤더의 선언도 씁니다. 이 선언이 쓰는 다른 헤더의 선언도 함께 씁니다. 프런트엔드가 거부하는 헤더는 에러(exit 1)이고, 그 `file:line:col`을 가리킵니다.

매핑 규약은 다음과 같습니다.

- C의 정수와 부동소수 타입은 그 타깃에서 같은 크기의 Nabi 원시 타입이 됩니다(`int` → `i32`, `long` → `i32` 또는 `i64`, `char` → `c_char`, `_Bool` → `bool`, `_Float16` → `f16`, `__bf16` → `bf16`). `size_t` / `uintptr_t` → `usize`, `ssize_t` / `intptr_t` / `ptrdiff_t` → `isize`. 시스템 헤더가 그런 타입에 붙인 typedef는 그 타입 자체입니다.
- typedef는 Nabi의 타입 별칭(type alias)이 됩니다.
- struct와 union은 `#[repr(C)] struct` / `union`에 대응합니다(타깃의 레이아웃상 필요하면 `#[repr(C, align(N))]`이나 `#[repr(packed)]`). 연속된 bitfield는 그 저장소를 덮는 바이트 배열 필드 `_bitfieldN` 하나가 됩니다. Nabi가 표현할 수 없는 레이아웃(N > 1인 `#pragma pack(N)`, union 안의 bitfield)은 같은 크기와 정렬로 `_opaque: [u8; N]`을 담은 struct가 됩니다. 선언만 되고 정의되지 않은 struct는 `struct Name;`(opaque)이 됩니다.
- enum은 그 정수 타입의 별칭과, 열거자마다 하나씩인 `const`가 됩니다(`pub type color = u32; pub const RED: color = 0;`). 이름 없는 enum은 그 상수들입니다.
- 객체 포인터(`T*`, `const T*`)는 `CPtr<T>`가 되며, `void*`는 `CPtr<u8>`가 됩니다.
- 배열 매개변수는 C가 조정하는 대로 포인터입니다(`char buf[16]` → `CPtr<c_char>`). 함수 타입 매개변수는 함수 포인터입니다.
- 함수는 `extern "C" fn`이 됩니다(C 가변 인자와, 프로토타입 없이 선언한 함수(`f()`)는 `...`). 32비트 x86 Windows의 stdcall 함수는 `extern "system"`에 들어갑니다. 전역 변수는 `static`이 됩니다(const가 아니면 `static mut`). static 함수와 inline 함수는 링크할 심볼이 없으므로 건너뜁니다.
- 함수 포인터는 `unsafe extern "C" fn(...) -> R | none`이 됩니다([refs-lang 5.9.4](../../refs-lang/005-modules/509-extern-block.md#c-함수-포인터-타입), NULL = `none`).
- 정수, 부동소수, 문자열 상수로 평가되는 object-like 매크로는 `const` 항목이 됩니다.
- Nabi 키워드나 원시 타입 이름인 C 이름에는 뒤에 `_`가 붙습니다. 함수와 static은 `#[link_name]`으로 C 심볼을 유지합니다.
- 그 밖의 것은 `// skipped ...` 주석을 남기고 건너뜁니다. 128비트 정수, `__fp16`, 8바이트보다 넓은 `long double`, 벡터와 블록 타입, 가변 인자 함수 포인터, 스레드 지역 변수, 다른 호출 규약이 여기에 듭니다. 바이트로 적은 struct(`_opaque`)는 절대 값으로 넘기지 않습니다. 그런 struct를 직접 또는 다른 struct 안에 담아 받거나 돌려주는 함수나 함수 포인터는 건너뜁니다. C는 그런 struct를 필드 단위로 분류하기 때문입니다.

### bindgen이 읽는 C

프런트엔드는 시스템 헤더가 쓰는 확장을 포함한 C17을, clang이 그 타깃에서 읽는 대로 읽습니다.

- 전처리기: 타깃의 미리 정의된 매크로(`__x86_64__`, `_WIN32`, `__APPLE__`, `__SIZEOF_LONG__`, MSVC 타깃의 `_MSC_VER`와 그 밖의 타깃의 `__GNUC__` 등), `#include`, `#include_next`, `__has_include`, `defined`, `__has_attribute`, `__has_builtin`, `__has_feature`를 쓰는 `#if` 산술, `#`, `##`, `__VA_ARGS__`, `__VA_OPT__`를 쓰는 object-like / function-like 매크로, `_Pragma` / `__pragma`, `#pragma pack`, `once`, `push_macro` / `pop_macro`. 그 밖의 pragma는 무시합니다.
- 선언: `__attribute__((..))`, `__declspec(..)`, `[[..]]`, `__asm__("symbol")` 레이블, nullability 한정자, `__extension__`, `typeof`, `_Alignas`, `_Atomic`, `_Static_assert`, 익명 struct와 union, bitfield, flexible array member, 고정 타입 enum, 블록 포인터(`^`), 벡터 타입. 함수 본문과 초기화식은 건너뜁니다(`nabicc`는 이를 읽고 컴파일합니다, [refs-lang 9.13](../../refs-lang/009-tools/913-c-compiler.md)).
- clang 자신의 헤더를 대신하는 내장 헤더(`stddef.h`, `stdint.h`, `stdarg.h`, `stdbool.h`, `limits.h`, `float.h` 등). 여기에는 intrinsic 헤더도 듭니다. x86에서는 `immintrin.h`, `x86intrin.h`와 `mmintrin.h` .. `nmmintrin.h`, `wmmintrin.h` 계열(MMX부터 SSE4.2, AVX, AVX2, FMA, F16C, BMI, BMI2, LZCNT, POPCNT, AES, PCLMUL, CRC32까지는 프로토타입으로, AVX-512와 AMX는 함수 없이 타입만), Arm에서는 `arm_neon.h`, `arm_acle.h`, `arm_fp16.h`, `arm_bf16.h`, MSVC 타깃에서는 `intrin.h`(x86에서는 `x86intrin.h`를 함께)입니다. intrinsic은 각각 본문 없는 선언이고, 바인딩하지 않습니다. 벡터 타입(`__m128`, `__m256i`, `float32x4_t` 등)은 위와 같이 건너뛰고, 그런 타입을 담은 struct는 바이트가 됩니다. 다른 아키텍처에서 이런 헤더를 포함하면 clang에서처럼 에러입니다(Arm에서 `#include <immintrin.h>`).
- 레코드 레이아웃은 타깃의 규칙을 따릅니다. System V 또는 Microsoft의 bitfield, `#pragma pack`, `packed`, `aligned`, `__declspec(align)`, `mode`.
- 상수 식(배열 크기, enum 값, bit 폭, 정렬, `_Static_assert`, 매크로 값)은 정수, 부동소수, 문자, 문자열 리터럴, enum 상수, 캐스트, `sizeof`, `_Alignof`, `offsetof`(`__builtin_offsetof`, 또는 `&((T *)0)->m`)와 산술, 비트, 비교, 논리, 조건 연산자로 이루어집니다.

방언은 `-std=`와 관계없이 GNU C17입니다. 읽지 못하는 것은 그 `file:line:col`에서 에러이고, 대신 무엇을 쓸지 알립니다.

| 구성 | 대신 쓸 것 |
|------|-----------|
| K&R 스타일 함수 정의(`int f(a, b) int a; ..`) | 프로토타입: `int f(int a, int b)` |
| 암시적 `int`(`static x;`) | 타입을 씀: `static int x;` |
| 평가할 수 없는 배열 크기, enum 값, bit 폭, 정렬(다른 `__builtin_` 호출, `_Generic`, 문장 식) | 위 형태의 정수 상수 식 |
| 알 수 없는 타입 이름 | 쓰기 전에 그 선언, 또는 그것을 선언하는 헤더의 `#include` |
| 찾을 수 없는 헤더 | `--` 뒤에 `-I <dir>` / `-isystem <dir>`. 이 기계의 플랫폼이 아닌 타깃이면 그 타깃의 헤더(`-isystem <dir>` 또는 `--sysroot <dir>`) |

## 1.7.7. 호출 안전 책임 분배

호출 지점에서 누가 무엇을 책임지는지 정리합니다.

| 항목                    | 책임자                         |
|-------------------------|--------------------------------|
| 포인터 null 검사        | C → Nabi 시 Nabi 코드            |
| 버퍼 길이 검증          | Nabi 코드 (길이를 알아야 함)    |
| 문자열 null 종료        | CString 생성 시 자동           |
| GC pin                  | Nabi 코드, C에 넘기는 GC 객체 안의 모든 포인터에 대해 ([1.6.5](106-gc-pin.md#165-pin이-필요한-때)) |
| C가 쥐는 Nabi 값        | Nabi 코드, `Handle`로 (1.7.10) |
| 메모리 해제 (`free`)    | Nabi 코드 또는 안전한 래퍼      |
| 호출 규약 일치          | extern 선언자                  |
| C 타입 크기             | extern 선언자, `c_*` 이름으로 (1.7.9) |
| 스레드 안전성           | C 라이브러리 문서 따름         |
| Errno / GetLastError    | 선언에 `#[errno]` (1.7.11)     |
| C가 부른 함수의 panic   | 런타임이 abort하거나 `#[on_panic]` 값을 돌려줌 ([refs-lang 5.9.12](../../refs-lang/005-modules/509-extern-block.md#5912-ffi의-안전성-책임)) |

모든 `extern "C"` 호출은 스레드를 park하므로(1.7.1), 아무리 짧은 C 호출 중에도 수집이 돌 수 있습니다. GC 객체 안을 가리키는 포인터(리스트의 버퍼, `StrBuf`의 바이트)는 객체가 pin된 동안에만 호출 중에 유효합니다. 예외는 `str` 인자 하나로, 그 루트가 문자열을 제자리에 둡니다([1.6.5](106-gc-pin.md#165-pin이-필요한-때)). 컴파일러가 알아서 pin을 빼는 일은 없습니다.

1. GC와 FFI의 통합. `Pinned<T>` guard와 `using` 블록을 함께 써서 자원 누수와 pin 누락을 함께 막습니다.

## 1.7.9. C 타입: `c_int`, `c_long`, `c_void`

`bare::ffi::types`는 C의 정수 타입과 부동소수점 타입에 타깃의 C 컴파일러가 정하는 크기대로 이름을 붙입니다. prelude에 모두 있으므로 선언에 `use`가 필요 없습니다.

| 이름 | C 타입 | Nabi 타입 |
|------|--------|-----------|
| `c_schar` / `c_uchar` | `signed char` / `unsigned char` | `i8` / `u8` |
| `c_short` / `c_ushort` | `short` / `unsigned short` | `i16` / `u16` |
| `c_int` / `c_uint` | `int` / `unsigned int` | `i32` / `u32` |
| `c_long` / `c_ulong` | `long` / `unsigned long` | Windows와 32비트 타깃에서 `i32` / `u32`, 그 밖에서 `i64` / `u64` |
| `c_longlong` / `c_ulonglong` | `long long` / `unsigned long long` | `i64` / `u64` |
| `c_size_t` / `c_ssize_t` | `size_t` / `ssize_t` | `usize` / `isize` |
| `c_ptrdiff_t` | `ptrdiff_t` | `isize` |
| `c_intptr_t` / `c_uintptr_t` | `intptr_t` / `uintptr_t` | `isize` / `usize` |
| `c_wchar` | `wchar_t` | Windows에서 `u16`, arm과 aarch64 Linux에서 `u32`, 그 밖에서 `i32` |
| `c_float` / `c_double` | `float` / `double` | `f32` / `f64` |
| `c_void` | 포인터 뒤의 `void` | 빈 struct |

`c_char`는 따로 있는 언어 타입입니다([2.15.5](../200-core/215-string.md#2155-c_char-c-abi-1바이트언어-내장)).

각 이름은 타입 별칭(`pub type c_int = i32;`)이고, 타깃마다 `#[cfg]`로 고릅니다. 한 타깃에서 `c_int`와 `i32`는 같은 타입이므로 값이 변환 없이 오갑니다. 고정 크기 타입은 C의 타입과 맞는 곳에서만 옳습니다. `fn labs(x: i64) -> i64`는 64비트 Linux와 macOS에서는 맞지만, `long`이 32비트인 Windows에서는 틀립니다. `c_long`으로 쓰면 그 선언은 모든 타깃에서 맞습니다.

`c_void`는 포인터 뒤의 C `void`를 나타내는 빈 struct입니다. `CPtr<c_void>`는 `void*`, `ConstPtr<c_void>`는 `const void*`입니다. `c_void` 값을 만들거나 읽는 일은 없습니다.

```nabi
extern "C" {
    fn labs(x: c_long) -> c_long;
    fn strlen(s: str) -> c_size_t;
}

let x: c_long = -3;
println(f"{unsafe { labs(x) }} {unsafe { strlen("abc") }}");    //→ 3 3
let p: CPtr<c_void> = CPtr::null();                             // null void*
```

## 1.7.10. `Handle<T>`: C가 쥐는 Nabi 값

콜백하는 C API는 `void* user_data`를 받아 콜백에 넘깁니다. `Handle<T>`는 그 포인터로 Nabi 값을 실어 나릅니다.

```nabi
// bare::ffi
#[repr(transparent)]
struct Handle<T> { /* handle 번호, 포인터 크기 */ }

impl<T> Copy for Handle<T> {}

impl<T> Handle<T> {
    fn new(value: T) -> Handle<T>;                     // 마지막 release까지 value를 살려 두고 제자리에 둠
    unsafe fn from_ptr(p: CPtr<c_void>) -> Handle<T>;  // C가 돌려준 handle
    fn as_ptr(self) -> CPtr<c_void>;                   // C에 넘길 void*
    fn get(self) -> T;                                 // 값
    fn set(self, value: T);                            // handle의 모든 복사본이 보는 값을 바꿈
    fn retain(self);                                   // 값을 놓기 전 release를 하나 더 요구
    fn release(self);                                  // new와 retain 횟수만큼 release하면 값을 놓음
}
```

`Handle::new`는 값을 GC 셀에 넣고, handle이 그 셀을 루트로 잡고 pin합니다. C가 포인터를 쥔 동안 수집이 몇 번 돌든, 값은 마지막 `release`까지 살아 있고 주소도 그대로입니다. `get`은 `List`, `Dict` 같은 공유 값이면 같은 객체를 돌려주므로, 리스트에 push하는 콜백은 호출자의 리스트를 바꿉니다. 일반 값(정수, struct)은 복사해 꺼냅니다. `retain`은 포인터의 복사본을 하나 더 두는 C 코드를 위한 것입니다. `retain`마다 `release`가 하나 더 필요합니다.

포인터는 handle 번호이고, null도 주소도 아닙니다. C는 그것을 통해 읽으면 안 됩니다. `Handle<T>`는 `Copy`이고 포인터 크기이며 `CPtr<c_void>` 위의 `#[repr(transparent)]`이므로, `#[repr(C)]` struct의 필드가 될 수 있습니다. `Clone`과 `Debug`를 구현합니다.

`from_ptr`는 `unsafe`입니다. `p`는 `Handle::<T>::new(..).as_ptr()`에서 와야 합니다. `get`, `set`, `retain`, `release`는 handle을 검사하고, 잘못되었으면 panic합니다.

- 마지막 `release` 뒤(또는 handle이 아닌 값): ``handle already released (or not a handle): call `release` once per `Handle::new` and `retain`, and not `get` after the last one``
- 만들 때와 다른 타입: ``this handle holds `List<str>`, not `Dict<str, i64>`: write `Handle::<List<str>>::from_ptr(p)` ``

클로저도 다른 값과 같은 값입니다. 클로저 자신의 타입은 쓸 수 없으므로 `fn` 타입으로 담습니다. `Handle::<fn(c_int)>::new(|x: c_int| ..)`입니다. `Handle::new(closure)`로 만들어 `Handle::<fn(i32)>`로 읽으면 ``this handle holds a closure, not `fn(i32) -> ()`: make it with `Handle::<fn(i32) -> ()>::new(..)` and read it with `Handle::<fn(i32) -> ()>::from_ptr(p)` ``로 panic합니다.

C 콜백은 아무것도 캡처하지 않는 `extern "C" fn`입니다([refs-lang 5.9.10](../../refs-lang/005-modules/509-extern-block.md#5910-extern-fn-정의외부에-노출)). C에서 클로저를 부르려면 클로저를 handle에 담고, 그것을 다시 읽어 부르는 한 줄짜리 `extern "C" fn`을 넘깁니다. 제네릭 trampoline은 없습니다. 클로저를 C 함수에 바로 넘기면 에러이고, 그 help가 이렇게 하라고 알려 줍니다.

```nabi
use bare::ffi::Handle;
use bare::ptr::CPtr;

extern "C" {
    // void each(int n, void (*cb)(void *, int), void *user_data);
    fn each(n: c_int, cb: extern "C" fn(CPtr<c_void>, c_int), ud: CPtr<c_void>);
}

extern "C" fn on_row(ud: CPtr<c_void>, i: c_int) {
    let rows = unsafe { Handle::<List<str>>::from_ptr(ud) }.get();
    rows.push(f"row {i}");                     // 호출자의 리스트
}

extern "C" fn call(ud: CPtr<c_void>, i: c_int) {
    let f = unsafe { Handle::<fn(c_int)>::from_ptr(ud) }.get();
    f(i);
}

let rows: List<str> = [];
let h = Handle::new(rows);
unsafe { each(3, on_row, h.as_ptr()) };
h.release();                                   // rows.len() == 3

let total = Cell::new(0);
let f = Handle::<fn(c_int)>::new(|x: c_int| { total.set(total.get() + x); });
unsafe { each(5, call, f.as_ptr()) };
f.release();                                   // total.get() == 10
```

런타임 쪽은 `nabi_handle_new` / `nabi_handle_get` / `nabi_handle_retain` / `nabi_handle_release`입니다([refs-lang 8.5.12](../../refs-lang/008-abi/805-extern-symbols.md#8512-보조-심볼부록-비규범)).

## 1.7.11. `#[errno]`: errno와 `GetLastError`

```nabi
#[errno]
extern "C" {
    fn open(path: str, flags: c_int, ...) -> c_int;
}

extern "C" {
    #[errno]
    fn chdir(path: str) -> c_int;
}

// bare::ffi
fn errno() -> c_int;            // 이 스레드의 마지막 #[errno] 호출이 남긴 errno
fn set_errno(v: c_int);         // 저장된 값과 C 라이브러리의 errno
fn last_error() -> u32;         // Windows: 그 호출이 남긴 GetLastError, 그 밖에서는 0
fn set_last_error(v: u32);      // 저장된 값과, Windows에서는 SetLastError
```

C 호출이 돌아온 뒤 다음 줄까지 스레드는 런타임 코드를 돌 수 있습니다. 네이티브 상태에서 나올 때 수집이 끝나기를 기다릴 수 있고, `str` 인자의 복사본을 unpin합니다. 그 코드가 errno를 바꿀 수 있습니다. `extern "C"`나 `extern "system"` 블록, 또는 그 안의 선언 하나에 `#[errno]`를 붙이면, 호출은 돌아오자마자 다른 무엇보다 먼저 errno(Windows에서는 `GetLastError`도)를 스레드별 슬롯에 저장합니다. `errno()`와 `last_error()`는 저장된 값을 읽으므로 언제 불러도 그 호출의 값입니다.

속성이 없으면 아무것도 저장하지 않습니다. `errno()`는 그 스레드의 마지막 `#[errno]` 호출(또는 `set_errno`)이 남긴 값을 돌려줍니다. `set_errno`는 저장된 값과 C 라이브러리의 errno를 함께 바꿉니다. errno로만 에러를 알리는 C 함수(`strtol`: 0을 넣고, 부르고, 읽음)를 위한 것입니다. `io::IoError::last_os_error()`([2.23.0](../200-core/223-io.md#2230-ioerror))는 저장된 값으로 `IoError`를 만듭니다. Windows에서는 저장된 `GetLastError`가 0이 아니면 그것을, 아니면 저장된 errno를 씁니다.

```nabi
use bare::ffi::{errno, set_errno};

let fd = unsafe { open("/no-such-dir/file", 0) };     //→ -1
let e = io::IoError::last_os_error();                 // e.kind() == NotFound, e.os_code() == 2
set_errno(0);
```

다른 항목의 `#[errno]`는 에러입니다. 함수에 붙이면 `` `#[errno]` cannot be attached to a function; it goes on an extern block or an extern function ``이고, `extern "nabi"` 블록(런타임은 errno를 스스로 지킴)에 붙이면 `` `#[errno]` and `#[leaf]` are for C declarations: put them on an `extern "C" { .. }` block or its functions ``입니다.

## 1.7.12. `WideCStr` / `WideCString`: `wchar_t` 문자열

Windows의 `W` API와 C의 `wchar_t` 함수는 NUL로 끝나는 `c_wchar` 단위 문자열을 받습니다. 이 타입들이 그런 문자열을 담습니다. Windows에서는 UTF-16, 그 밖에서는 char 하나에 단위 하나(UTF-32)입니다. API는 모든 타깃에서 같습니다.

```nabi
struct WideCString { .. }      // 비공개 필드 (0.5.10)

impl WideCString {
    fn new(s: str) throws (NulError) -> WideCString;   // s를 단위와 NUL로; NulError::position()은 단위 인덱스
    fn as_ptr(self) -> ConstPtr<c_wchar>;
    fn as_wide_cstr(self) -> WideCStr;
    fn as_units(self) -> Slice<c_wchar>;               // NUL 제외
    fn to_str(self) -> str;                            // 원래 문자열; 실패하지 않음
    fn len(self) -> usize;                             // NUL 앞의 단위 수
}

struct WideCStr { .. }

impl WideCStr {
    unsafe fn from_ptr(p: ConstPtr<c_wchar>) -> WideCStr | none;   // NUL까지 복사; null → none
    fn as_ptr(self) -> ConstPtr<c_wchar>;
    fn as_units(self) -> Slice<c_wchar>;               // NUL 제외
    fn as_units_with_nul(self) -> Slice<c_wchar>;
    fn to_str(self) throws (Utf16Error) -> str;
    fn to_str_lossy(self) -> str;                      // 잘못된 단위마다 → U+FFFD
    fn len(self) -> usize;
}
```

둘 다 단위와 NUL을 GC 객체 하나에 담고, `Clone`, `PartialEq`, `Eq`, `Hash`, `Debug`(`WideCString("hi")`)를 구현합니다. `as_ptr`는 `CStr::as_ptr`와 같은 기간 동안 유효합니다(1.7.2). `from_ptr`는 `CStr::from_ptr`처럼 C 문자열을 복사해 옵니다. `p`는 null이거나 살아 있는 NUL 종료 `wchar_t` 문자열을 가리켜야 합니다. `WideCString::new`는 `str` 안의 NUL에서 `NulError`(1.7.2)를 던집니다. `WideCStr::to_str`는 Windows에서는 짝 없는 surrogate에서, 그 밖에서는 char가 아닌 단위에서 `str::Utf16Error`([2.15.6](../200-core/215-string.md#2156-utf-8-불변식-프로세스-안의-모든-문자열))를 던집니다. `valid_up_to()`는 그 단위 인덱스입니다.

NUL과 포인터 없는 UTF-16 자체는 `str::encode_utf16`, `str::from_utf16`, `str::from_utf16_lossy`입니다(2.15.6). C가 채우는 버퍼는 pin한 `List<u16>`이고, `str::from_utf16`으로 다시 읽습니다.

```nabi
// Windows
use bare::ffi::WideCString;
use bare::gc::pin;
use bare::ptr::{ConstPtr, Ptr};

extern "system" {
    fn SetEnvironmentVariableW(name: ConstPtr<u16>, value: ConstPtr<u16>) -> i32;
    fn GetEnvironmentVariableW(name: ConstPtr<u16>, buf: Ptr<u16>, size: u32) -> u32;
}

let name = try WideCString::new("NABI_WIDE_TEST");
let value = try WideCString::new("h\u{E9}\u{1F600}");
unsafe { SetEnvironmentVariableW(name.as_ptr(), value.as_ptr()) };

let buf: List<u16> = [];
for _ in 0..1024 { buf.push(0u16); }
let held = pin(buf);
let n = unsafe { GetEnvironmentVariableW(name.as_ptr(), held.as_data_ptr(), 1024u32) };
let back = try str::from_utf16(buf[0:n as usize]);     //→ "hé😀"
```

## 1.7.13. `Library`: 공유 라이브러리 불러오기

```nabi
struct Library { .. }

impl Library {
    fn open(path: str) throws (LoadError) -> Library;
    fn this() -> Library;                                          // 프로그램 자신
    fn raw_symbol(self, name: str) throws (SymbolError) -> CPtr<c_void>;   // null이 아님
    unsafe fn symbol<F>(self, name: str) throws (SymbolError) -> F;        // F: C 함수 포인터 타입
    unsafe fn close(self) throws (LoadError);
}

struct LoadError { .. }
impl LoadError {
    fn path(self) -> str;        // open에 준 경로
    fn message(self) -> str;     // 시스템이 준 이유
}

struct SymbolError { .. }
impl SymbolError {
    fn name(self) -> str;        // 찾은 심볼
    fn message(self) -> str;     // 시스템이 준 이유
}
```

`open`은 실행 중에 공유 라이브러리를 불러옵니다. Unix에서는 `dlopen(path, RTLD_NOW | RTLD_LOCAL)`, Windows에서는 `LoadLibraryW`입니다. 경로 없는 이름은 시스템의 라이브러리 경로에서 찾습니다. `this()`는 프로그램 자신입니다. Unix에서는 자기 심볼과 함께 링크된 모든 라이브러리의 심볼, Windows에서는 실행 파일이 내보내는 것만입니다. `raw_symbol`은 심볼의 주소를 줍니다. `symbol::<F>`는 함수를 `F`로 줍니다. `F`는 C 함수 포인터 타입(`extern "C" fn(f64) -> f64`, `extern "system" fn() -> u32`)이어야 하고, 다른 타입이면 주소를 그 타입으로 바꾸기 전에 panic합니다. `` `symbol::<i32>`: write the C function pointer type, `extern "C" fn(..) -> R` ``입니다. `F`가 심볼의 진짜 시그니처여야 하므로 `unsafe`입니다.

라이브러리는 저절로 내려가지 않습니다. `Library`에는 `Drop`이 없고, `close`가 유일한 방법입니다. `close` 뒤에는 라이브러리에서 얻은 모든 포인터(심볼, 그것이 돌려준 데이터)가 매달리므로 `close`는 `unsafe`입니다. `this()`를 닫으면 아무 일도 없습니다. `Library`는 `Clone`과 `Debug`(`Library("kernel32.dll")`, `Library(this)`)를 구현합니다.

메시지는 시스템의 것(`dlerror`, `FormatMessageW`)입니다. `LoadError`는 `cannot load {path}: {message}`(`close`에서는 `cannot close ..`)로, `SymbolError`는 `cannot find symbol {name}: {message}`로 표시됩니다. 경로나 이름 안의 NUL은 시스템에 묻기 전에 에러입니다(`the path has a NUL byte at 1; remove it`). 둘 다 `Display`, `Debug`, `Error`, `PartialEq`, `Eq`, `Clone`을 구현합니다. 동적 로딩이 없는 타깃(wasm32, OS 없음)에도 타입은 있고, `open`이 `this target has no dynamic loading`으로 던집니다.

```nabi
use bare::ffi::Library;

fn main() throws (bare::ffi::LoadError | bare::ffi::SymbolError) {
    let lib = try Library::open("libm.so.6");
    let cos = try unsafe { lib.symbol::<extern "C" fn(f64) -> f64>("cos") };
    println(f"{unsafe { cos(0.0) }}");                      //→ 1
    try unsafe { lib.close() };
}
```
