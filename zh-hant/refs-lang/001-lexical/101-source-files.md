# 1.1. 原始檔

本節涵蓋 Nabi 原始檔的實體格式：檔案在磁碟上必須如何編碼，以及編譯器開始讀取第一個位元組時有哪些假設。

## 1.1.1. 副檔名

Nabi 原始檔的副檔名是 `.nabi`。其他副檔名，例如 `.no` 或 `.nabir`，不會被辨識為 Nabi 原始碼。

## 1.1.2. 字元編碼

> [!IMPORTANT]
> 原始檔必須以 **UTF-8** 編碼。

以 UTF-16、GBK 或 Shift_JIS 等其他編碼撰寫的檔案會立即被編譯器拒絕。編譯器不嘗試自動偵測編碼，因為猜測錯的時候比對的時候多。檔案開頭的 BOM（`U+FEFF`）會被默默忽略；出現在其他任何位置時，它是一個不可見字元（見下文）。

### 禁止雙向控制字元

雙向（bidi）控制字元 U+202A-202E 與 U+2066-2069 出現在原始碼的任何位置（包括註解與字串字面值）都是編譯錯誤。這可以防止顯示出的程式碼與實際語彙單元順序不同的攻擊。若字串需要其中某個字元，請用 `\u{202E}` 之類的跳脫序列撰寫。

### 不可見字元

不顯示任何東西的字元不會被讀作程式碼：零寬空格、零寬非連接符與零寬連接符（U+200B-200D）、由左至右與由右至左標記（U+200E、U+200F、U+061C）、字詞連接符與不可見運算子（U+2060-2064）、位於檔案開頭之後的位元組順序標記 U+FEFF、軟連字號 U+00AD、韓文填充字元（U+115F、U+1160、U+3164、U+FFA0），以及不修飾任何字元時的異體字選擇器（U+FE00-FE0F、U+E0100-E01EF）與標籤（U+E0000-E007F）。在程式碼中以及識別字內，每一個都是編譯錯誤，錯誤訊息會指出該字元；U+0020 與 tab 以外的空格（例如 U+00A0 NO-BREAK SPACE）也是如此（請寫一般空格）。在字串、字元字面值或註解中，這樣的字元會產生 `hidden_chars` 警告（[6.2.9](../006-meta-system/602-built-in-attributes.md#629-allow--deny--warn-lint-控制)）：請把它寫成 `\u{..}` 跳脫序列，讓讀者看得見。連接符出現在它應有的位置時不會被回報：emoji 序列中的 ZWJ、異體字選擇器或標籤（`👨‍👩‍👧`、`❤️`），以及會用到 ZWNJ 的文字（波斯文、印度系文字）中字母之後的 ZWNJ。

### 形似字元與未指派字元

只是看起來像 ASCII 語彙單元的字元是編譯錯誤，錯誤訊息會指出應該寫的語彙單元：`−`（U+2212 MINUS SIGN）應寫 `-`，彎引號應寫 `"` 與 `'`，全形字元（`（`、`；`、`＝`）等也是如此。若套件把這樣的字元註冊為運算子語彙單元（[1.10.4](110-punctuation-and-operator-tokens.md#1104-擴充語彙單元)），它就成為該套件自己的語彙單元，此時不會被回報。Unicode 18.0.0 尚未指派的碼位在程式碼中是錯誤，在字串與註解中則產生 `hidden_chars` 警告。

診斷以碼位與 Unicode 名稱（`U+200B ZERO WIDTH SPACE`）指稱這樣的字元，只有在字元可見時才顯示字元本身。

## 1.1.3. 行終止符

下列三種都被辨識為邏輯行的結尾。

- LF（`U+000A`）
- CRLF（`U+000D U+000A`）
- CR（單獨的 `U+000D`）

即使這三種形式混用在同一個檔案中，編譯器也會接受，因為無論檔案是在哪裡產生的，它都必須能運作。本規格建議只使用 LF。

其他分隔行的碼位，例如 `U+2028` LINE SEPARATOR 或 `U+2029` PARAGRAPH SEPARATOR，不是行終止符。它們在識別字或字串中以一般碼位的身分出現。

## 1.1.4. 行與檔案大小的限制

本規格對行長度、檔案大小或識別字長度不設上限。編譯器可以施加合理的限制，但這些限制是實作上的決定，不屬於規格。

## 1.1.5. 診斷中的位置單位

編譯器診斷（錯誤、警告）以檔案、行與欄提供位置。

行號從 1 開始。欄是從行首起以碼位計算（是碼位，不是位元組）、從 1 開始的索引。因此像韓文音節這樣的多位元組字元只占一欄。tab（`U+0009`）也只占一欄，不模仿其視覺寬度。

這些規則讓機器（編輯器與 LSP）容易處理診斷位置。視覺上的對齊交給顯示工具。
